## Lane map (V1, measured by Spike A)

Setup: FP32 tiles in Dest (`fp32_dest_acc_en`, `UnpackToDestFp32`), an SFPU function called per face through the `VectorMode::RC` wrapper, each face being 8 SFPU vectors of 32 lanes, the host tilizing with `tilize_nfaces<float>`. Each lane wrote `(face*8 + vector)*64 + vConstTileId`, and the untilized output shows which one landed at each tile position.

- Faces are 16x16 and ordered row-major inside the tile: top-left, top-right, bottom-left, bottom-right. The SFPU's own face counter equals `(row/16)*2 + (col/16)` at all 1024 positions.
- Inside a face, for local `rr = row%16`, `cc = col%16`:
  - vector index `v = 2*(rr/4) + (cc & 1)`
  - lane `l = 8*(rr % 4) + cc/2`
  - `vConstTileId = 2*l = 16*(rr % 4) + (cc & 0xE)`; it takes 32 distinct even values, 0 to 62
- Inverse, which lets an SFPU kernel derive pixel coordinates with no coordinate tiles: `col = 16*(face&1) + (vConstTileId & 0xE) + (v & 1)`, `row = 16*(face>>1) + 4*(v>>1) + (vConstTileId >> 4)`.
- Consequence: the "derive coordinates from lane ids" fallback in the plan's risk table is available. Spike B generates the dx and dy tiles once per tile from lane ids and every result was exact. Deriving the coordinates again inside the triangle loop, instead of keeping the two tiles, was not measured; it would free two Dest slots at the cost of a few integer SFPU instructions per vector per triangle.
- Not measured: the same map in 16-bit Dest mode (an in-tree kernel comment suggests it differs for BF16). Phase 2 uses FP32.

## Multicast (Spike D, V-multicast)

Setup: one sender core multicasts 4 KB to a rectangle of worker cores, semaphore handshake (ready, flag, ack), every receiver poisons its buffer first and then verifies the pattern and writes a record to DRAM. `spikes/d_multicast`, one chip. Eleven rectangles including single core, row, column, interior block, right and bottom edges, all rows below the sender, sender at the far corner, sender mid-grid, and the full grid with the sender inside (loopback variant of the multicast calls). Every receiver of every rectangle verified (up to 119 of 119).

- NoC coordinates: the 12x10 worker grid sits at NoC x = 1..7 and 10..14, NoC y = 2..11. Worker columns are not contiguous in NoC space: x = 8 and 9 hold non-Tensix tiles. A rectangle spanning the gap (the full-grid multicast) still worked, so the gap needs no special handling for multicast. Always convert logical to NoC coordinates with the device API (`worker_core_from_logical_core`), never by arithmetic.
- Latency and bandwidth are in `docs/PERF.md`.
- Not tested: multicast to a rectangle that contains harvested columns on a different chip. Every chip presents the same logical grid; the logical to NoC map may differ per chip, so tray-wide code must use each device's own map.

## Single chip and full tray (Spike E)

- One binary, two modes (`spike_e unit` and `spike_e mesh`, chips chosen by `TT_VISIBLE_DEVICES`): the trivial program ran and verified on 1 of 1 device in unit mode and on 8 of 8 devices in mesh mode, on the 2x4 mesh of nodes 0-7.
- Mesh coordinates are topology-based, not node-ordered: mesh row 0 holds nodes 4, 5, 6, 7 and row 1 holds nodes 0, 1, 2, 3 (coordinates `[0,0]` to `[0,3]` and `[1,0]` to `[1,3]`). Assign screen regions by mesh coordinate, and look up the device with `mesh->get_device(coord)`.
- Host to chip bandwidth is link-limited and uneven: about 3.2 GB/s each way on an x1 chip (82% of the 3.94 GB/s Gen5 x1 limit), 19.8 GB/s write and 13 to 16 GB/s read on the x8 chip (numbers in `docs/PERF.md`). Reading all eight chips back at once reached only 11.3 GB/s in total with non-blocking per-shard reads, against about 37 GB/s if every link ran in parallel, so the read-back of multi-chip frames must be designed and measured, not assumed.
- Consequence for frame read-back: a 1920x1088 RGBA8 frame is 8.4 MB, which is 2.6 ms through one x1 link, so splitting the frame over eight chips and reading the pieces back concurrently is worth measuring in Phase 2.6; the x8 chip can carry a larger share of the screen.

## Tray topology and chip-to-chip (Spike E)

- Fabric control plane for nodes 0-7: one mesh of shape 2x4 whose X and Y axes are both a line (no wraparound inside the tray). Every chip has 12 of 14 Ethernet cores enabled (`ENABLED_ETH` in `tt-smi -s`); the per-pair link counts were not enumerated.
- Node, fabric chip id and mesh coordinate: fabric chip id is the row-major index in the 2x4 mesh, so fabric chips 0-3 are mesh row 0 = nodes 4-7, and fabric chips 4-7 are row 1 = nodes 0-3. Node `k` sits at tray position (`asic_location`) `k + 1` of tray 1.
- Fabric bring-up (`FABRIC_2D`, 8 devices) takes about 3.2 s, and it ran and shut down cleanly: afterwards all 32 chips still answered `tt-smi`, DRAM status was fine, and the Ethernet status values had the same distribution as before.
- Chip-to-chip bandwidth measured with the in-tree `bench_unicast` (one sender core to one receiver core, 4 KiB pages, through the fabric; built by reconfiguring the tt-metal build with `-DTT_METAL_BUILD_TESTS=ON` and building only that target): 10.5 GB/s between horizontal neighbours and also across three hops along a row, 14.8 GB/s to the vertical neighbour and also to the diagonal chip. So extra hops cost no bandwidth, and the vertical direction is faster than the horizontal one for a single stream. These are single-stream numbers; several cores or several links in parallel were not measured. Small transfers are latency-bound: 4 KiB takes 3.5 us and 64 KiB 9.2 us.
- Consequence: chip-to-chip traffic inside the tray is about 3x the x1 host link per stream and comparable to the x8 host link, so passing intermediate results between chips costs less than a trip through the host.

## Dest layout for Phase 2 (confirmed 2026-11-10)

Budget: FP32 half-sync gives 4 tiles and keeps pack overlapped with the next tile's math; FP32 full-sync gives 8 tiles but serializes pack and math. Phase 2 stores color as one packed RGBA8 word per pixel, so color needs one tile instead of four FP32 planes. Per-triangle plane equations for depth and color are evaluated in SFPU registers, not stored.

| Slot | Half-sync layout (4 tiles) | Full-sync layout (8 tiles) |
| --- | --- | --- |
| 0 | depth (FP32) | depth |
| 1 | color, RGBA8 packed as a 32-bit integer | color RGBA8 |
| 2 | dx (from lane ids, generated once per tile) | dx |
| 3 | dy | dy |
| 4 to 7 | not available | coefficient tile (scalar path B), triangle id or alpha plane, two spare |

Scalars use path A (L1 runtime immediates) in both layouts, so no slot is reserved for coefficients in the half-sync layout. Recommended scalar path for Phase 2: A, triangle-major, with compile-time-unrolled bodies for a full tile and a runtime-bounded loop for partial coverage. Path B has the lowest delivery cost (about 16 versus 37 cycles per triangle) but takes a Dest slot and 32x more data per triangle, and A is within 7% of the no-scalar baseline for a full-tile triangle; revisit B if the profile shows scalar delivery above roughly 10%. Do not use C (programmable constants) or vector-major order with A. Deriving dx and dy from `vConstTileId` inside the triangle loop instead of keeping them as tiles would free slots 2 and 3, but costs a few integer SFPU instructions per vector per triangle, against two loads: keep the tiles unless slots are needed.

## Phase 1: CPU reference, setup and test infrastructure

Code is in `src/ttraster/` (a host library with no tt-metal dependency), tools in `tools/` (`ttr_render`, `ttr_diff`), tests in `tests/`, golden images in `tests/golden/`. Build and test with `scripts/build.sh` and `scripts/test.sh` (no device needed). All six test programs pass under clang 20 (tt-metal's toolchain) and gcc 11, and the golden hashes are identical under both compilers.

### Pipeline and the numeric contract

1. **Snap** vertices to 1/16 pixel (round to nearest, ties to even). Reject non-finite and out-of-range input, zero-area triangles (after snapping) and, optionally, one winding.
2. **Edge functions** are integers: `E(P) = a*Px + b*Py + c` with `a = y0 - y1`, `b = x1 - x0`, `c = -a*x0 - b*y0`, positive inside. A pixel centre is at `16*i + 8` subpixels, so `E` is an integer there. The top-left rule is folded into `c`: an edge that is not top or left gets `c - 1`, so every edge uses the same `E >= 0` test (top-left means `a > 0` or `a == 0 and b > 0` in y-down coordinates).
3. **Tile-relative evaluation.** Per (triangle, tile) the host computes `c_t`, the edge value at the tile centre, exactly in int64 and rounds it once to FP32. A pixel's offset from the tile centre is `16*i - 248` subpixels (exact). The device and the reference compute `E = fma(a, ddx, fma(b, ddy, c_t))`, two multiply-adds, and test `E >= 0`. Depth and each colour channel use the same shape: `v = fma(gx, ddx, fma(gy, ddy, v_t))` with `v_t` the plane value at the tile centre.
4. **Exactness bound.** The coefficients must satisfy `|a|, |b| <= 2^15`. Then `c_t` is representable whenever an edge crosses the tile (`|c_t| <= 248 * (|a| + |b|) < 2^24`), every partial sum that matters is below 2^24, and the sign of `E`, including `E == 0`, equals the int64 result. Measured over 41 million pixels at the 2^15 bound and 20 million at each larger one (`tests/test_edge_exactness.cpp`):

   | Coefficient bound | Pixels with E exactly 0 | Wrong signs, contract order | `(a*ddx + b*ddy) + c` | fused first step, then `+ c` | `(c + a*ddx) + b*ddy` |
   | --- | --- | --- | --- | --- | --- |
   | 2^15 | 175,801 | 0 | 0 | 0 | 0 |
   | 2^16 | 83,014 | 391 | 391 | 391 | 391 |
   | 2^17 | 86,009 | 6,384 | 5,857 | 5,857 | 6,379 |
   | 2^18 | 89,678 | 12,337 | 11,654 | 11,654 | 12,362 |

   So the bound is tight (it fails right above it, for every order), and within it the evaluation order does not matter. That settles the plan's open question: **no exact int32 path is needed**, provided every triangle that reaches the device has `|a|, |b| <= 2^15`. A multiply-add that is only partially fused (V10) gives the same signs, because inside the bound no intermediate needs rounding.
5. **Guard band.** `2^15` subpixels is 2048 pixels, so the render target is limited to 2048 x 2048 and every triangle is clipped to a rectangle that is exactly 2048 pixels wide and high (the viewport plus a symmetric guard band: 64 px each side at 1920 wide, 480 px each side at 1088 high). Triangles inside need no clipping. Others go through Sutherland-Hodgman clipping in integer subpixels, and the polygon is fanned into triangles. A cut edge's new end point depends only on the edge's two end points, not on their order, so two triangles that share an edge clip it identically and stay watertight. Planes are fitted from the original unclipped snapped vertices and shared by the pieces, so colour and depth of a clipped triangle are exact (verified at the viewport corners of the screen-covering scene, which needs 49,000-subpixel edges: 0 LSB colour error).
6. **Binning.** Tile bounding box from the pixel centres that can lie inside the vertex bounding box, then exact per-tile classification from the four extreme pixel centres: Reject (dropped, no work on the device), Partial, or Full (every pixel inside, so a device can skip the edge tests; verified by rendering with and without the shortcut). Bins keep API order.

### Reference rasterizer and oracle

- `render_reference` evaluates exactly as above and writes packed RGBA8, depth, the id of the visible triangle, a coverage count (triangles whose edge tests hit the pixel) and an *ambiguous* flag (a depth comparison within 1e-6 relative; Phase 2 can use it to excuse pixels where the device's 1 ulp difference may flip two nearly coincident surfaces).
- Colour quantization is `clamp(floor(v * 255 + 0.5), 0, 255)`, NaN is 0. Smooth interpolation is exact to 0 LSB against barycentric coordinates in double; depth to 7.4e-8.
- The **int64 oracle** decides coverage from the integer edge values with no tiles, no FP32 and no precomputed `c`. `oracle_cover_from_setup` (post-clip triangles) must equal the reference exactly and does, on every scene at 1920 x 1088. `oracle_cover_from_input` (no clipping at all) must also agree everywhere clipping cannot have touched; it does, and for the screen-covering triangle it agrees even inside the clip mask, because the cut edges lie outside the viewport.
- **Watertightness (Phase 1 DoD).** The jittered grid mesh of 4,080 shared-vertex triangles at 1920 x 1088 covers every one of the 2,088,960 pixels exactly once and none twice. The 96-triangle fan has no pixel hit twice. The random-vertex stress test (4,000 triangles on a 256 x 160 target plus 600 on 1920 x 1088, half of them on the half-pixel grid so that many pixel centres lie exactly on edges, vertices spread over the whole guard band so edge coefficients reach the 2^15 limit) has 0 coverage mismatches.

### Incident: scenes were not portable

The first gcc build of the goldens failed for the three scenes that draw several random numbers inside one function call. C++ leaves argument evaluation order unspecified (clang goes left to right, gcc right to left), so the same seed gave different scenes. Every draw is now its own statement. Rule for new scenes and tests: never put two RNG draws in one expression.

## Phase 2: Tensix rasterizer v1

Code: `src/tensix/` (host renderer, multi-chip driver, kernels), `tools/ttr_device` and `tools/ttr_multichip`, acceptance script `scripts/test_device.sh`. Numbers are in `docs/PERF.md`.

### Result

The device image is **bit-identical to the CPU reference and to the committed golden PNGs** for every scene at 1920 x 1088 on one chip (all 120 worker cores), and the 2, 4 and 8-chip images are bit-identical to the single-chip image. Coverage (checked by a separate debug run that counts covering triangles per pixel), visible triangle id and colour agree exactly on every pixel; the only differences are in depth, at most 2.4e-7 (one FP32 ulp at depth near 1), on pixels that the reference flags as depth-ambiguous, and even there the colour agrees. Exact depth ties under LESS_EQUAL (65,499 pixels in `coplanar_lequal`) also agree with no tolerance (`--strict`).

So the V10 concern about the SFPU's partially fused multiply-add did not matter: edge tests are exact by construction (docs: Phase 1, evaluation contract), and the depth and colour planes came out equal to `std::fmaf` on these inputs.

### Design

- **Work lists.** The host builds one 128-byte record per (tile, triangle) pair from the Phase 1 setup: three edges `(a, b, c)`, depth plane `(c, gx, gy)`, four colour planes, triangle id, flags, and a 2-bit class per SFPU vector. Records are grouped in 4 KiB pages (32 records, one FP32 tile, so a circular-buffer page is a tile). A tile block is a header record plus its records, padded to whole pages. Cores get contiguous, cost-balanced runs of tiles (`split_balanced`: 1.5 + records per tile, which is within 0.5% across 8 chips on `random_10k`).
- **Kernels.** The reader streams pages from DRAM into a 4-page circular buffer; the compute kernel clears the tile, draws every record, quantizes colour once and packs; the writer writes the planes. One program for all cores, per-core runtime arguments.
- **Dest layout used:** FP32 full sync, 8 tiles: depth, R, G, B, A, dx, dy, triangle id. The Phase 0 proposal (half sync, packed RGBA8 in one tile) was implemented too, behind `RASTER_PACKED_COLOUR`, and measured: within about +/-10% of the planes layout on most scenes, 4% slower on `random_10k` and 38% slower on a single full-screen smooth triangle (per-pixel quantization of four channels is about 25 extra SFPU instructions per vector), a few percent faster on flat-colour scenes (a flat triangle stores one constant, and no per-tile quantization pass). Planes were kept as the default because they cost nothing in capacity here and do not penalize smooth shading; packed + half sync stays available and is the layout to use if Dest slots are ever needed.
- **Per-vector classes (the big win).** The host classifies every one of the 32 SFPU vectors of a tile exactly, from the four extreme pixel centres (plus a bounding-box reject): class 0 = no pixel inside (skipped by the kernel), 2 = every pixel inside (no edge tests), 1 = partial. On the test scenes 82% of vectors are rejected. `tests/test_classify.cpp` checks every class against plain int64 per-pixel tests (0 wrong in 867,000 vectors).
- **Plan item 2.2** (a scalar bounding-box check on the math thread) is not needed: the host's exact tile and vector rejection already removes everything that cannot touch the tile or the vector, and a record never reaches the device otherwise.
- **Multi-chip** (2.6): bands of tiles per chip (same balanced split), one `render()` per chip from its own host thread, all writing disjoint tiles of one shared framebuffer. No chip-to-chip traffic.

### Per-core L1 budget

Kernel code: unpack 0.8 KB, math 8.3 KB, pack 1.6 KB, reader 0.8 KB, writer 1.0 KB (12.5 KB in total). Circular buffers: triangle pages 4 x 4 KiB = 16 KiB, output planes 2 x 4 KiB each: 8 KiB for colour only, 24 KiB with the depth and id debug planes. Total 36 to 52 KiB of the 1,536 KiB per core (2.3 to 3.4%). There is room for much deeper buffering.

### What we learned about the hardware and tt-metal

1. **The math RISC-V core is the bottleneck, not the SFPU.** It issues every SFPU instruction as a store of the instruction word, so the cost of a vector is the cost of *building and pushing* its words: about 2.4 RISC-V cycles per SFPU instruction here, against 1 SFPU cycle. Runtime vector indices (`dst_reg[slot*32 + v]`) cost three RISC-V instructions per load or store. Using the destination counter (`dst_reg++`, constant offsets) makes each word a constant: -23% time. Float scalars delivered as immediates (V5 path A) cost two `SFPLOADI` words each per use, and a full vector with smooth colour uses about 50 of them, which is why the cost per vector is about 135 cycles (depth and colour) plus 83 cycles for three edge tests. Cost model measured on `random_10k`: about 5 us per tile of fixed work, about 135 cycles per fully covered vector, about 220 per partial vector, and about 0.3 ms of launch (0.75 ms with 120 cores).
2. **Colour writes are 54% of the triangle time** (ablation: removing the colour stores took `random_10k` from 2.95 to 1.82 ms). SIMD predication does not skip work, so a depth pre-pass cannot avoid colour work per vector; it would only add a second pass. Not implemented, for that reason.
3. **MATH to UNPACK release.** The math thread reads records straight from the L1 page, but `cb_pop_front` runs on the unpack thread with no ordering against the math thread's loads, so the reader can refill a page that is still being read. tt-metal's own `triangle_solve_tile` has the identical problem and solves it with a message from MATH to UNPACK before the pop; the kernel does the same (`mailbox_write(UnpackThreadId)` / `mailbox_read(MathThreadId)`). Bit-exact output on millions of pixels shows it holds.
4. **SFPU registers cannot be spilled.** Eight vector registers; code that keeps too many `vFloat` or `vUInt` live fails at link time with "cannot read/write SFPU object from memory". It also appears when a helper that passes vectors is not inlined: mark such helpers `always_inline`. Packing four colour channels into one word needed accumulating through Dest instead of registers.
5. **Integer and packing idioms that work.** `sfpi::convert<vUInt16>(x, RoundMode::Nearest)` with `<<` and `|` quantizes and packs; `dst_reg[i] = vUInt` is a raw 32-bit integer store (the SFPSTORE INT32 mode); the packer to a Float32 circular buffer passes the bits through unchanged, including patterns that look like NaN (alpha 255 puts 0xFF in the top byte). `sfpi::reinterpret` does not exist in this SFPI version. `dst_reg += n` takes n in [-4, 3] only.
6. **Batching several records into one SFPU call did not help** (start and done steps are cheap), and rewinding the destination counter between records needs eight `dst_reg += -4`; not kept.
7. **Several devices in one process must be opened together** with `MeshDevice::create_unit_meshes`. Opening unit meshes one after the other left the first chip's first program hanging (the process was stopped by the run script's timeout; nothing else was affected and no reset was needed, the chips ran normally afterwards). With `create_unit_meshes` two to eight chips run concurrently from one process.
8. **Host costs matter as soon as the device is fast.** A fresh multi-megabyte allocation costs page faults that serialize badly across threads: with eight chips each encoding and reading back on 64 threads, "build" went from 8 ms (one chip) to 28 ms (eight). Reusing buffers between frames, writing straight into one shared framebuffer, and giving each chip its share of the host threads brought it back to about 3 ms. Encoding the records is 80,000 pairs x 32 vector classifications per `random_10k` frame, 19 ms on one thread, 5 ms on 64.

### Open items

- Per-triangle cost is still dominated by instruction issue. Ideas not tried: keep more scalars in SFPU registers across vectors by splitting a triangle into passes with at most four scalars; the coefficient-tile path B from Spike B with a table built per triangle; `SFPREPLAY` / `SFPLOADMACRO` to cut the issue cost (Phase P).
- Per-frame fixed cost is now host side: record encoding, upload of the work lists, and read-back (8.4 MB over one x1 PCIe link is 2.6 ms at best). Overlapping frames (pipelining host build, upload, device and read-back) would hide most of it.
- Only one core's DRAM channel assignment and the 12 x 10 grid were used as given; no attempt was made to place cores near their DRAM banks.

## Track I: Isaac Lab renderer backend

### I.1 Interface study (Isaac Lab 3.0.0, commit 94e8c23 of 2026-11-10, read from source)

Sources read: `isaaclab/renderers/{base_renderer,output_contract,camera_render_spec,renderer_cfg,render_context}.py`, `isaaclab/sensors/camera/camera.py`, `isaaclab_newton/renderers/{newton_warp_renderer,newton_warp_renderer_cfg}.py`, `isaaclab_tasks/core/cartpole/cartpole_common.py`, `isaaclab_tasks/utils/presets.py`, and Newton's `SensorTiledCamera` and ray-tracing kernels.

**Contract of `isaaclab.renderers.BaseRenderer`.** Constructed as `Renderer(cfg, *, sim)`; the instance is shared by every camera whose config resolves to it (`SimulationContext.get_or_create_backend`). Abstract methods: `supported_output_types() -> dict[RenderBufferKind, RenderBufferSpec(channels, warp dtype)]`, `prepare_stage(stage, num_envs)`, `create_render_data(spec: CameraRenderSpec)`, `set_outputs(render_data, output_data: dict[str, ProxyArray])`, `update_transforms()`, `update_geometries()`, `update_camera(render_data, positions, orientations, intrinsics)`, `render(render_data)`, `read_output(render_data, camera_data)`, `cleanup(render_data)`. Optional: `initialize()` (once, after physics), `prepare_capture(render_data, camera_data, frame)` (async delivery), `update_camera_intrinsics(render_data, intrinsics, parameters)` (raises NotImplementedError by default), `render_batch(list)` (default loops over `render`), `reset(render_data, env_ids)`, `close()` (idempotent), `visual_material_writer`.

**Call order.** Camera construction: `get_or_create_backend(cfg.renderer_cfg)`; `RenderContext.ensure_prepare_stage` -> `prepare_stage(stage, num_envs)` once; camera initialization: `create_render_data(spec)`, `supported_output_types()` (requested `data_types` are checked against it), `set_outputs(render_data, camera_data.output)`. Every capture: `update_camera(...)` (poses, then intrinsics), `prepare_capture(...)`, then `RenderContext.render_into_cameras`: `update_transforms()`, `update_geometries()` once per renderer, `render_batch([render_data...])`, then `read_output(render_data, camera_data)` per camera. Environment resets call `reset(render_data, env_ids)`.

**Data types and placement.** Everything is Warp arrays on the simulation device (`cuda:N`) wrapped as `ProxyArray` (`.warp`, `.torch` zero-copy views). `positions` is `(N,)` `wp.vec3f` (torch `(N, 3)`), `orientations` `(N,)` `wp.quatf` as (x, y, z, w), `intrinsics` `(N,)` `wp.mat33f`. Output buffers are allocated by the camera from `supported_output_types()`: Newton Warp publishes `rgba` (4 x uint8), `rgb` (3 x uint8), `rgb_hdr` (3 x float32), `albedo` (4 x uint8), `depth`, `distance_to_camera`, `distance_to_image_plane` (1 x float32), `normals` (3 x float32), `semantic_segmentation` and `instance_segmentation` (4 x uint8 colourised, or 1 x int32 ids), shaped `(N, H, W, C)`. No motion vectors. Background depth is 0.0 (not +inf); `depth_clipping_behavior` in {none, zero, max}; the far clip comes from the camera's `clipping_range`.

**Scene input.** The renderer builds its own scene from the cloner (`cloning_contexts`) and the USD stage; body transforms come each step from `sim.get_scene_data_provider()` (`create_mapping(body_labels)`, `get_transforms(poses, mapping, count)`). Newton Warp keeps a Newton model, ray traces analytic shapes (box, sphere, capsule, plane) and meshes, and maps its per-shape index to semantic and instance ids on the host.

**Presets.** `renderer_cfg` fields are `PresetCfg`s; `MultiBackendRendererCfg` in `isaaclab_tasks/utils/presets.py` lists `rtx`, `ovrtx`, `isaacsim_rtx`, `newton_renderer` and `default` (Newton Warp). A new backend is a `RendererCfg` subclass whose `class_type` names the implementation (string `"module:Class"` supported); to make it selectable from the CLI it needs a field in that preset class (a one-line change in Isaac Lab, or a task-local preset subclass).

**Shading model of the reference (to match).** Albedo: sRGB shape colour converted to linear. Ambient: hemispheric, `sky (0.4, 0.4, 0.45) * h + ground (0.1, 0.1, 0.12) * (1 - h)` times 0.5, `h = 0.5 * (n.z + 1)`. One directional light with direction (-1, 1, -1)/sqrt(3) (light vector L = -direction), contribution `albedo * max(0, n.L)` (no shadows by default), then linear to sRGB. Pinhole rays: camera looks down -z with +x right and +y up; pixel centres at (p + 0.5) / size; `film = (u - 0.5) * aperture`, ray = normalize(film_x / f, film_y / f, -1). `depth` is the distance along the unit ray, `forward_depth` the distance projected on the camera axis.

**The cartpole camera task** (`Isaac-Cartpole-Camera`): 96 x 96 pixels (nine tiles), one tiled camera per environment, offset (-5, 0, 2) in the world convention, focal length 24 mm, horizontal aperture 20.955 mm, clipping range 0.1 to 20 m, data type chosen by preset (`rgb` default, `depth`, `albedo`, `semantic_segmentation`).

**Not verifiable on this host.** Isaac Lab itself needs PyTorch and CUDA (its tensors, Warp arrays and physics live on the GPU), so the shim cannot be run inside Isaac Lab here, and whether any CPU physics path exists was not tested. What can be tested: the renderer core against Newton's ray tracer, which runs on the CPU through Warp (below), and the shim's logic through a stand-in for `BaseRenderer`.

### Incident: chip 0 stuck after a hang, and how it was recovered (2026-11-11)

A depth-only request (plane mask without the colour plane) hung chip 0. Cause: the compute kernel configured the packer from circular buffer `c_16`, which does not exist when the colour plane is not requested. The kernel now uses the first requested plane's buffer. The run was stopped by the script timeout, and afterwards opening chip 0 failed during initialization ("Memory barrier timed out ... 10 of 130 cores synced"); chips 1 to 7 were unaffected. (While chip 0 was down, subsets of chips that are not a connected part of the tray mesh, such as nodes 1 to 4 or 1 to 7, failed in fabric control-plane setup with `TT_FATAL control_plane.cpp:1806`; nodes 4 to 7 and 5 to 6 worked.)

Recovery (the user gave standing permission to reset chips): `tt-smi -r 0` reset only chip 0 and single-chip programs worked again, but the 8-chip mesh still failed (`Physical chip id 0 not found in control plane chip mapping`), because chip 0's Ethernet links were not back in the fabric. `tt-smi -glx_reset_tray 1` is not supported here ("UMD warm reset only supports full galaxy reset"), and a full Galaxy reset would have reset the other trays, one of which had a running program from another session, so it was not used. `tt-smi -r 0,1,2,3,4,5,6,7` (per-device resets of the tray's eight devices; the list matters, with no list tt-smi resets everything) brought the mesh back. Verified afterwards: all 32 chips still answer `tt-smi`, the other session's process on tray 4 was untouched, and the full acceptance (`scripts/test_device.sh`: crops, full frame, exact depth ties, 1, 2, 4 and 8 chips, 8 scenes, images identical across chip counts) passes on nodes 0 to 7.

## Track G: OpenGL through Mesa (softpipe fast path)

What exists and how it was checked; the user-facing description is `mesa/README.md`.

**Design.** Instead of a new Gallium driver (the plan's G.2 forks softpipe), softpipe itself gets a small patch (`mesa/patches`, 284 lines, plus the new `sp_tensix.c`): a full colour+depth clear opens a rasterizer frame; draws that libttraster can do hand their post-transform triangles to it from `sp_setup_tri` (after softpipe's own sorting, culling and facing decision); the frame is rendered once at flush and written into the colour buffer's memory. Anything else is drawn by softpipe after the pending frame was rendered and written back, so the output is never wrong, only slower. A new driver name (`GALLIUM_DRIVER=tensix`) and `TTR_GL` switch it on. This kept the diff small and keeps GLSL, fixed function, clipping, culling and polygon offset in Mesa.

**Perspective-correct varyings were needed after all.** The plan assumed glxgears needs only flat or linear colours; Mesa's fixed-function colour varying is perspective-interpolated (GL requires it), so every draw was refused at first. A first attempt accepted triangles whose perspective error stays below half a colour step (bound: range * (R - 1) / 2 with R = w_max / w_min) and fell back otherwise, but glxgears exceeded it constantly. The rasterizer now interpolates perspective-correctly: `Triangle::perspective` makes setup fit planes of colour * rhw and of rhw; the reference divides per pixel; the Tensix kernel multiplies the planes by `approx_recip` refined with two Newton steps (the 1/w plane uses record words 29 to 31, which were free). The device can differ from the reference's IEEE division in the last float bit, so perspective scenes allow one colour level in the acceptance tools (`ttr_device`, `ttr_multichip`); the new scene `perspective` (a receding floor and 20 large triangles) has 12 such pixels of 2.09 million, the OpenGL scene 0.6 %, because triangles of one colour sit on exact rounding boundaries (0.5 * 255). `tests/test_perspective.cpp` checks the reference against an analytic per-pixel computation (within one level, including a cropped triangle) and the cases that must not take the perspective path.

**Bugs worth remembering.** (1) softpipe derives its vertex layout and setup info lazily, when the draw module first asks; inspecting `setup_info` at the start of a draw saw stale zeros (call `softpipe_get_vbuf_vertex_info` first). (2) `1.0f * 16777215.0f + 0.5f` rounds to 2^24 in float and overflowed into the stencil byte of a Z24S8 depth buffer: compute in double. (3) The tile caches are write-back with lazy clear flags; writing a whole surface directly means invalidating the cache entries and the clear flags first (the colour surface is then written as words, about 0.7 ms at 1080p; through the cached float tiles it took 6 to 10 ms).

**Per-triangle depth and blend state.** Whole-frame batching broke on every state change, which made blending and depth-mask tricks fall back to softpipe. Each triangle now carries its own state (`Triangle::own_state`, `depth_func` LESS/LESS_EQUAL/ALWAYS, `depth_write`, `blend`), so batches with different state share a frame and stay in API order. Blending works on the unquantized FP32 colour planes the device already keeps in Dest (softpipe also blends in float tiles); the fragment colour is clamped, then `r = clamp(s * A + d * B)` with the coefficients of one table (`kBlendCoef` in `raster_layout.h`, shared by the host reference and the kernel: alpha, add, premultiplied, multiply, alpha-add), so no mode switch is needed in the vector code. The reference keeps float colours when a frame has blended triangles. In the kernel, records with default state keep the specialized path (unchanged, 3.5 us per record on `random_10k`); records with own state take a general path (a flag bit selects it, depth function and blend decoded per record, ALWAYS is LESS against 3e38): about 11.5 us per record on the `state` scene, whose busiest core has few records, so its fixed per-tile cost weighs in. The `state` scene (60 triangles, every mode) is exact against the reference on 2,088,960 pixels with one pixel one level off, and identical on 1, 2, 4 and 8 chips. GL semantics worth noting: with the depth test off Gallium neither tests nor writes depth (an earlier version of the driver wrote it).

**Where GLSL stands.** Vertex shaders of any complexity run on the host in Mesa's draw module. Fragment shaders were at first only a colour pass-through; G.6 (below) translates arithmetic fragment shaders to the chip. Mesa here is 26.3.0 built with only softpipe, GLX and GL 3.3 compatibility; no Vulkan, no conformance claim.

**Measured.** See `docs/PERF.md` ("OpenGL"): glxgears at 1920 x 1080 runs at 126 FPS on a Tensix chip against 31 FPS for stock softpipe; at 300 x 300 stock softpipe is faster (575 against 310 FPS) because a chip frame costs about 2 ms of fixed latency.

### G.6 Fragment shaders (in progress)

**Stage 1, host side (done): instruction set, interpreter, reference.** A fragment shader is a straight-line program over vector registers (`src/tensix/kernels/shader_isa.h`, shared by the host and the kernel): 22 instructions (Mov, Add, Mul, Mad, Min, Max, Frc, Flr, Rcp, Rsq, Sqrt, Ex2, Lg2, Sin, Cos, Slt, Sge, Seq, Sne, Cmp, Sel, Kill), operand modifiers (negate, absolute value, constant operands) and a saturate flag. No branches: conditionals are compare + select, which is what the SFPU predication gives anyway and what a translator from NIR/TGSI can always produce by if-conversion. Registers `r[0 .. num_inputs)` hold the pixel's interpolated varying components, an optional block holds `gl_FragCoord` (x, y of the pixel centre, interpolated z, interpolated 1/w), constants come from a per-program table (uniforms and literals), the result is a vec4 in `r[out ..]`. A program is rejected by `validate_shader` if it reads a register that was not written, so results never depend on stale Dest rows (which is also what makes the device comparable to the CPU run). 61 registers is the budget (`kMaxRegs`): the three Dest tiles that are free in a frame with an RGBA8 target (below) are 96 vector rows, and because the destination counter advances one vector per iteration, register r of vector v is row r + v of the region, so r + 31 must stay inside it (three more rows are the device's own: the active-lane flag and two blend coefficients).

**Semantics are defined by the CPU interpreter** (`run_shader`): IEEE binary32, round to nearest, `Mad` fused (single rounding, like the SFPU's multiply-add as measured for the planes). The transcendental instructions are libm on the host and SFPU approximations on the device; they will agree to a few ulps, not bit for bit, so the acceptance rule for shader frames will be the existing "one colour level" rule rather than exact equality. Everything else must be exact.

**Varyings reuse the plane machinery.** `Triangle::shader` selects a program of `Frame::shaders`, `Triangle::attr_offset` the triangle's varyings in `Frame::attrs` (num_inputs floats per vertex, vertex-major). Setup fits one screen-space plane per component (of `value * rhw` for perspective triangles, plus the rhw plane that also feeds `gl_FragCoord.w`); per tile the planes are made tile-relative like colour (`make_tile_plane`), and a pixel's varying is `fma(gx, dx, fma(gy, dy, c))`, times the reciprocal of the rhw plane for perspective triangles. A pass-through shader (`out = varyings 0..3`) renders bit-identically to the fixed-function colour path, linear and perspective (`tests/test_shader.cpp`). Discard (`Kill`) leaves colour, depth and id alone; the depth test runs before the shader, a killed fragment writes nothing.

**A frame with shader triangles has an RGBA8 target.** Colour is quantized with every write and blending reads the quantized colour back (`byte * (1/255)`), as on a GPU. Frames without shaders keep the old behaviour (unquantized float colour while drawing). The reason is the device: packing colour into one Dest slot is what frees the three tiles that hold shader registers. The reference follows the same rule so that the two stay comparable; a test shows the difference (blending 25 % white over mid grey: byte 160 on an RGBA8 target, 159 on a float one).

**Builder API lesson.** The hand-written program builder first had two `emit` overloads, one taking a destination register number and one not; passing a register number where an operand was expected compiled, validated (operands default to register 0) and rendered a wrong but plausible sphere. Operands are now a distinct type (`Src`), the destination form is `emit_to`, and the mistake no longer compiles.

**Test scene `shader`** (golden image, 1920 x 1088): a background from `gl_FragCoord`, a perspective checkerboard floor, a Phong-lit sphere (rsq, lg2/ex2 specular), a discard "screen door", and an alpha-blended layer with sin-modulated alpha and depth writes off. The Tensix renderer refuses frames with shaders for now (the tools skip the scene) until stage 2.

**Stage 2, device interpreter (done).** Frames with shader triangles run a separate compute kernel variant (`RASTER_SHADERS`, with the packed-colour variant) built around `ckernel_sfpu_shader.h`; frames without shaders use exactly the kernels they used before. What was built:
- *Records.* A shader record keeps the 128-byte layout: its first four varying planes sit where the colour planes are (words 12 to 23), the program id in word 28, the rhw plane in 29 to 31; components beyond four go into 1 to 3 extension slots after the record (3 words per component), so a record takes 1 + ext slots and never straddles a 4 KiB page (the first unused slot of a page whose tail is too short holds a marker). Fixed-function records of such a frame have no shader flag and are drawn as "four inputs, no instructions, colour in registers 0 to 3". The block header gets the page count (the page count is no longer derived from the record count), and the tile centre as floats, which `gl_FragCoord` needs.
- *Program table.* One table per frame (directory, code, constants) goes first in the input buffer; the reader copies it once into a 16-page circular buffer, the math thread reads it from L1.
- *Interpreter.* Per 32-lane vector: the active flag (inside the triangle, depth test passed) is computed first, then the varyings from the planes, then the program instruction by instruction (operands fetched with runtime-indexed `dst_reg`, the opcode as a RISC-V `switch`, one SFPU operation per case), then the colour is quantized and packed (or blended against the unpacked old colour) under the active flag. Kill clears the flag. Transcendentals are written for the SFPU: `rcp` (estimate plus Newton), `rsq` (bit trick plus three Newton steps), `ex2` (integer part into the exponent field, degree 5 polynomial, 1.2e-7 relative), `lg2` (exponent plus an odd series), `sin`/`cos` (range reduction, fold to a quarter period, degree 11).
- *Two compiler facts.* (1) A function that is not inlined and is called from inside a `v_if` region does not keep the lane predicate: the first version (the shader body in a `noinline` function) drew garbage on every partial vector (edges of triangles) and left the middle of triangles right. Everything is inlined at one call site, and the lane predicate is carried in a Dest register (the "active" flag) so that no heavy code sits inside nested `v_if` (and the nesting depth stays far from the CC stack limit). (2) The sfpi compiler crashed (internal error in out-of-SSA) on vector values that were conditionally defined across RISC-V branches; operands are now read unconditionally (unused operand words are zero and read register 0).
- *Offline compile loop.* The JIT build can be reproduced without a device (`-c` with LTO, then `-r -flinker-output=nolto-rel` to force LTO code generation), which turned a compiler crash into a one-second edit-compile cycle; a plain non-LTO compile crashes even on the old kernels and is not a valid proxy.

**Measured (device vs CPU reference).** The `shader` scene at 1920 x 1088 on one chip: 2,088,951 of 2,088,960 pixels exact, 9 one level off, ids and depth exact, golden image identical, and the same frame on 1, 2, 4 and 8 chips identical (`ttr_multichip`). All other scenes are unchanged (golden identical). Device time 4.6 ms (median 5.1 ms) per frame, 18 us per record on the busiest core; see `docs/PERF.md`.

**Instruction accuracy on the device** (`tools/ttr_shader_ops`: one pixel per test, 8192 tests per instruction with operands over six decades; the shader returns `0.5 + (op(a, b, c) - ref) * scale`, so the 8-bit colour reads the error back at half an ulp resolution; u = 2^-23 * max(|ref|, 1)): Mov, Add, Mul, Min, Max, Frc, Flr, Slt, Sge, Seq, Sne, Cmp, Sel exact; Mad within 1 u of max(|a*b|, |c|, |ref|) (the SFPU multiply-add keeps the product to about 2^-23 of its size, so a cancelling sum is off by up to 5 u of the *result*, as the plane arithmetic always was); Rcp 1.0 u, Rsq 1.5 u, Sqrt 2.0 u, Ex2 2.0 u (x in +-30), Lg2 1.0 u, Sin and Cos 2.0 u (|x| up to 50). The first version of Cos (shifting by pi/2 before the range reduction) was 8.5 u: the shift rounds the large argument; it is applied after the reduction now. Device and CPU interpreter differ by at most 4 colour levels of the amplified error image, i.e. by two ulps.

**Stage 3, the Mesa side (done): TGSI to shader programs, on a chip.** `mesa/softpipe_tensix/sp_tensix_shader.c` (about 800 lines of C) translates the TGSI Mesa produces for a fragment shader (NIR to TGSI is Mesa's own step; softpipe consumes TGSI) into this instruction set; the driver registers the program with the open frame (`ttr_frame_shader`, identical programs of a frame share an id, uniforms are read into the constant table at every draw) and submits the triangles with their varyings (`ttr_frame_triangles_shaded`). Design:
- *Per-component expansion.* TGSI is vec4: every instruction becomes one to a few scalar instructions per enabled component. Swizzles and negate/absolute value are operand modifiers, saturate is the instruction flag, scalar instructions (RCP, RSQ, SIN, DP3, POW, ...) compute once and copy to the other enabled components, and an instruction whose destination overlaps its own sources (`MUL T0.xyz, IN.xyzz, T0.xxxx`) computes into scratch first, which is the only way TGSI's read-before-write semantics survive component-wise emission.
- *Conditionals by if-conversion.* `IF/ELSE/ENDIF` run both sides: a mask register (cond != 0, multiplied with the parent's mask, inverted for the else side) selects between the new and the old value at every write inside; `KILL_IF` inside a branch kills only where the mask is set. Loops that NIR unrolled are straight-line; a loop with run-time bounds is refused (the shader falls back to softpipe).
- *Register allocation.* The code is straight-line, so a linear scan over live ranges is enough: at most 57 registers for inputs, `gl_FragCoord` and values, the four colour outputs in the four registers above them; operands are read before the result is written, so a result may take the register of an operand that dies in the same instruction.
- *`gl_FragCoord` conventions.* Mesa's TGSI states its convention in properties (origin lower-left, pixel centre half-integer) and softpipe delivers the coordinate accordingly (`sp_setup.c`: y counted from the bottom); the rasterizer's coordinate is the pixel centre from the top, so the translator inserts `y' = height - y` (the framebuffer height is a per-draw constant slot) and `x - 0.5` for an integer pixel centre. The first stripes test, a pattern of `fract(gl_FragCoord.x * k + gl_FragCoord.y * k')`, was wrong on 15 % of the pixels until then.
- *Booleans.* NIR's comparisons arrive as `FSLT`/`FSGE` giving an integer mask, consumed by `UCMP`, `IF`, `AND mask, 1.0f` (boolean to float) or the logic of `&&`, `||`, `!` (`AND`, `OR`, `XOR`, `NOT` of two masks). The instruction set's compares produce 1.0 or 0.0, so `UCMP` is a select on non-zero, the `AND` with the bits of 1.0 is a move, and the mask logic is Mul (and), Max (or), Sne (xor) and Seq-with-0 (not). Registers that hold a comparison result are tracked while translating (a compare, mask logic on such registers, a move of one, the constants 0 and all-ones); a write under a lane mask makes a register a comparison result only for the lanes of that mask, so reads inside the region count, reads after the ENDIF do not unless both sides of an IF/ELSE wrote one or the value it overwrote was one. Any other integer or bitwise operation is refused. **Found by `mesa/tests/fuzz_glsl.py`:** the short-circuit form of `a || b` that NIR writes for a non-trivial `b` stores the constant "true" (all ones, `0xffffffff`) in the ELSE branch; as a float that is a NaN, so the first translator put a NaN where a 1.0 belonged and the `discard` below it never fired (3.8 % of a test image wrong, no refusal, no message). The constant is 1.0 in the translator now.
- *Varyings.* Each input component a shader reads gets a register; constant-interpolated inputs take the provoking vertex's value at all three vertices; perspective and screen-linear inputs cannot be mixed in one triangle (refused).

**Random GLSL shaders (`mesa/tests/fuzz_glsl.py`).** The translator is the other place where a mistake would be silent, so shaders are generated from a seed (typed expression trees over varyings, uniforms and `gl_FragCoord`, locals of float to vec4 with swizzles and write masks, nested `if`/`else`, constant-trip loops, `discard`, `&&`/`||`, the common built-ins), drawn on a sphere by stock softpipe, which interprets the TGSI itself, and by the fast path (CPU backend, or a chip), and compared: the share of pixels more than 4 levels apart, and more than 16. The first 120 shaders found two things: `&&` and `||` made 34 of the 106 valid shaders (32 %) fall back to softpipe (mask logic was not translated), and after that the all-ones constant above. With both fixed, 600 shaders (seeds 1 to 600): all 600 take the fast path, 479 draw something other than the background, 175 are bit-identical to softpipe, the mean share of pixels more than 4 levels off is 0.013 % and the worst image 1.0 % (more than 16 levels: 0.75 %; in a further 300 shaders the worst image was 2.1 % and 0.78 %, a shader of `step`, `sign`, `mod` and nested comparisons; `floor`, `fract`, `step` and compares turn a one-ulp difference into a flipped pixel). 40 shaders on a chip: worst 0.09 %. `scripts/test_gl.sh` runs 150 on the CPU backend and 12 on the chip. The same 300 shaders, 100 random GL frames and es2gears also ran against a Mesa built with AddressSanitizer (translator and driver included): no memory error.

**Random GL frames (`mesa/tests/fuzz_gl.py`, `gl_fuzz.c`).** The state handling of the fast path (depth function and writes, the five blend pairs, flat and smooth shading, culling and winding, strips, fans, quads and polygons, clipped and crossing geometry, orthographic and perspective projections, and now and then state it refuses, which hands the rest of the frame to softpipe) is compared against stock softpipe on random frames. The two rasterizers differ in edge rounding and depth interpolation, and where two surfaces meet at a shallow angle they pick different surfaces over a whole band (z-fighting, visible as a checker pattern in softpipe), so the limits are statistical (4 % of pixels per run, 0.5 % mean over the runs). Calibration by mutation of the driver: Premultiplied blending mapped to Add gives a mean difference of 3.8 % and 71 of 150 runs over the limit; the flat colour taken from the first vertex of each triangle 7.7 % and 113 of 150; the driver as it is, 0.15 % mean and the worst run 2.2 % (`--tame`: moderate triangles, orthographic). With huge perspective triangles softpipe itself becomes noisy: mean 0.32 %, worst run 6.6 %. 150 runs of two frames with every draw on the fast path, and 150 with a rare refused draw (66 runs fell back in the middle of the frame): all within the limits; 30 and 20 runs on a chip: mean 0.13 % and 0.09 %. The depth function LEQUAL against LESS cannot be told apart this way (it differs only where depths are equal).

**Signed zero on the device.** An arithmetic fragment shader exposed that the SFPU compares the sign bit for `x < 0` and the raw word for `x != 0`: a real -0 (a negative number times zero, the negate modifier on +0) counted as negative and as non-zero. The pattern `discard` after `fract(x * k) < 0.4` (translated to `KILL_IF -mask`, so a -0 whenever the mask is 0) killed every fragment on the chip while the CPU backend was right. The compare, Cmp, Sel and Kill instructions now add +0 to their operands first (-0 + +0 is +0 under round to nearest, everything else is unchanged), so they follow IEEE (-0 == +0); `tools/ttr_shader_ops` tests every compare with operands that are real -0 (the first test missed it because a plane value `0 * dx + (0 * dy - 0)` is +0 by itself: the inputs must be negated inside the shader).

**Random programs (`tools/ttr_shader_fuzz`).** The per-instruction tests fix the operands, so they cannot catch an interaction between instructions, registers and lanes. The fuzz builds frames of 220 random triangles (large, small, slivers, partly off screen, linear and perspective varyings, random depth so that they overlap, own depth and blend state on a quarter of them, fixed-function triangles mixed in) that use up to 40 random programs of up to 960 instructions, 61 registers and 32 varyings (on some frames with viewports that clip every triangle against a rectangle, and with face culling), renders them on the chip and with the CPU reference, and compares colour, depth and triangle id of every pixel. Two modes, because the device evaluates the interpolated planes with a multiply-add that is not exactly fused, so an input can be one ulp off, and Frc, Flr, the compares, Cmp, Sel and Kill turn one ulp into a whole colour:

- `exact` (default): all 13 exact instructions with random operands, constants (including -0), negate and absolute-value modifiers, saturation and destinations anywhere in the register file (inputs included); the varyings are constant over each triangle and the programs read only x and y of `gl_FragCoord` (pixel centres), so every value is exactly representable on both sides and the device must agree bit for bit. With viewports and culling: 400 frames, 17.5 million pixels, and 150 frames with blending, 7.0 million pixels: all identical, with the same triangle ids. Also identical: 12 frames of 1920 x 1088 with 1,500 triangles (25 million pixels), and the frames split over 2, 4 and 8 chips (`--chips N`, 40 frames each; 4 frames of 1920 x 1088 with blending on 8 chips, 8.4 million pixels).
- `smooth`: varyings that vary, `gl_FragCoord` z and 1/w readable, but only Mov, Add, Mul, Mad, Min and Max, so one ulp stays one ulp: 9.1 million pixels (200 frames), four a level off, none further; with blending 4.6 million pixels (100 frames), three a level off, none further. The transcendental instructions are not in the fuzz: a one-ulp input error is amplified by them without bound for large arguments, and `ttr_shader_ops` measures each of them.

Programs that produce a NaN, an infinity or a subnormal on sampled inputs are discarded (the device flushes subnormals and has its own NaN rules), pixels whose depth test is ambiguous in the reference are skipped, and depth must agree within 4 ulp or 2e-6 plus a quarter of the rounding of a term of 16 pixels times the plane's gradient (the largest difference was 3.6e-6, on a sliver whose depth changes by 11 per pixel). **Bug found by the first run:** `Frc(-0)` returned 1 on the device: `floor` is the magic-constant rounding followed by `v_if (r > x) r -= 1`, and with x = -0 the compare reads the sign bit, so the floor of -0 came out as -1. A second flaw in the same code: the magic constant only rounds correctly for |x| < 2^22, so `Frc` and `Flr` were wrong from there on. `sh_floor_any` (add +0 first, take x itself from 2^22 on except for the one fraction bit of [2^22, 2^23)) fixed both; `ttr_shader_ops` now has `Frc-0`, `Flr-0` (a real -0 and tiny, near-integer, half-integer and huge values) and `FrcX`, `FlrX`, which fail on the old code (2,580 of 8,192 pixels) and pass now.

**Measured.** 12 fragment shaders in `mesa/tests/gl_scene.c` (`--fs`): Lambert and Phong per pixel, stripes from `gl_FragCoord`, `discard`, nested conditionals, a loop of `sin`, uniforms changing every frame, `smoothstep/mix/mod/floor`, write masks, fog from `gl_FragCoord.z`, an alpha computed by the shader (plus the old pass-through and `--glsl-alu`): every one is translated and drawn on the fast path, in the CPU backend and on a chip, against stock softpipe within 0.3 to 1.6 % of the pixels one level off (3.8 to 5.8 % for the shader with `floor` and `mod`, whose steps move on a rounding) and 0.01 to 0.1 % by more; chip against CPU backend within one level on 0.0015 % of the pixels. A shader with a loop of run-time bounds draws the stock result exactly (refused). `scripts/test_gl.sh` runs all of them. Interpreter cost and the GL frame times are in `docs/PERF.md`.

**What is not done in G.6.** Texturing (no texture units; sampling would be a gather from DRAM per pixel), derivatives, loops with run-time bounds (a real branch on the SFPU would need the whole vector to agree), integer arithmetic, more than one colour output, depth writes from the shader, and speed of the interpreter itself (about 40 ns per instruction and vector, 50 cycles: decode-bound).
